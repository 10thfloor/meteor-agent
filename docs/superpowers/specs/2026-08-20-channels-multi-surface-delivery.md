# Channels: letting your agent talk on Slack, SMS, and email

**Date:** 2026-08-21
**Status:** as built (shipped 2026-08-22); see errata below. Revised twice before building: once after examining the Flue framework, once after a survey of cross-channel rendering prior art (§13).
**Package:** `10thfloor:agent`

**As built — errata.** The design shipped as written, with these concrete differences folded into the sections below. The source of truth is `app/packages/agent/common/channel-contract.ts` (the lens contract — pure and isomorphic, so the channel packages and the core share one module) and `app/packages/agent/server/channels/{registry,ingress,egress,plan,linking,collections}.ts`; the channel packages are `app/packages/agent-channel-{slack,telegram,whatsapp,sms}`.

- `lens.in` takes one argument, `in(event)`; the envelope also carries `audience?` and `respond?` (§8.3, `common/channel-contract.ts`).
- The `prompt` item carries `toolCallId`; a receipt's `expects` entries are `{ match, verdict, toolCallId }` (§6.3, §8.2, `collections.ts`).
- Channel config has `verify` and `parse` — not a `signingSecret` — and the package factories supply both (§10, `registry.ts`).
- `onUncertainDelivery` is optional and defaulted, not required (§11, `registry.ts`).
- Throttled inbound events are dropped with a 200, not refused with a 429 (§9, `ingress.ts`).
- One-time approval and linking tokens are single-use random ids stored server-side, not signed tokens (§8.4, §12, `linking.ts`).
- `Agent.channel` ships in the package (§15); the side-action tool is an inline tool spec, not `Agent.tool` (§7).
- An anonymous `group` binding admits only its opener until someone links (§3, `ingress.ts`).

## 1. The idea

An agent already knows how to receive a message, think about it, and write an answer to the database. A browser user sees that answer because the web client subscribes to the database and paints it to the screen. A "channel" is just doing the same thing — reading the agent's answers from the database — but sending them to Slack, or as a text message, or as an email, instead of painting them on a web page.

So a channel is not a new system. It is two adapters bolted onto the existing machinery:

- **Inbound:** a webhook receives a Slack message (or SMS, or email), figures out which user sent it, and calls the same `send` function the web client uses.
- **Outbound:** a background worker watches the database for new agent replies and forwards them to the external service.
- **Lookup tables:** small tables that remember who an external user is, and which conversation is connected to which agent session.

The framework already does the hard parts (running the agent, storing messages, managing turns). Channels just translate at the edges.

**One conversation can live on several surfaces at once.** A support thread can be visible in Slack, mirrored over SMS, and open in the web app simultaneously — each surface tracking its own delivery progress independently.

### Why this is the only shape that fits

The package says two things clearly: "the extension surface is hooks, and only hooks" and "adding a second protocol beside DDP would be inventing a worse one." A channel design that adds a new hook or builds a parallel message pipeline breaks both promises. A channel that translates external messages into the existing `send` call, and reads answers from the existing database, breaks neither.

## 2. Decisions already made

| # | Decision | Why |
|---|---|---|
| 1 | No new engine — channels reuse what exists | The package's own rules say so. |
| 2 | The outbound worker copies the shape of the existing recovery watcher | That watcher already solved multi-server coordination, crash recovery, and duplicate prevention. |
| 3 | The outbound worker watches finished messages, not the live typing stream | Slack and SMS users want the complete answer once, not a stream of partial tokens. |
| 4 | Inbound messages go through the existing `send` function | That function already handles authorization, ordering, and budgets. |
| 5 | **Identity and routing are separate tables** | One person can reach the same agent from Slack, SMS, and email. Who they are is shared across all three; which conversation maps to which session is per-surface. |
| 6 | **The model never chooses where a message goes** | Destinations are derived from the session's own bindings, never from a tool argument. A tool argument is not an authorization boundary. |
| 7 | **Exactly-once admission; effectively-once delivery** | Duplicate inbound webhooks can be rejected outright. Duplicate outbound posts can only be made invisible, not strictly prevented. §11 is explicit about the line. |
| 8 | **Rendering out and interpreting in are one object — the lens** | On a surface with no buttons, "Reply YES to approve" only means something because the outbound render said so. The reply grammar is *generated by* the render; author the two halves separately and they drift (a documented failure in Microsoft's Bot Framework — §13). |
| 9 | **No universal message format between the row and the surface** | The canonical form is the committed message row the harness already writes. Microsoft couldn't make one card language render consistently across its own hosts (§13). Surfaces get semantic structure and encode it natively. |

## 3. What's in scope

**This design covers:** how messages get in, how replies get out, the two small additions to the framework itself, the three lookup tables, the rendering layer (the lens), how the outbound worker runs safely across multiple servers, delivery guarantees, and account linking.

**Deferred to a build plan:** the wire specifics of any one provider (Slack API details, Twilio, SMTP).

**Not in scope by design:** live token streaming to non-web surfaces. The live typing stream exists for the browser; every other surface is turn-at-a-time.

**Scoped to single-human conversations for v1.** A binding carries one owner, and every call into the agent is owner-scoped (§5.1). A group thread — several humans talking to one agent in one Slack channel — needs an ownership model the framework doesn't have: the second human's `send` would fail the ownership check by design. Group conversations are an open question (§15), not a silent gap. As built, an anonymous group binding admits only its opener (ingress.ts) until someone links.

## 4. How it works

### 4.1 The symmetry

The web client and a channel do the same thing — read the agent's messages — with different outputs:

```
Web:      [Messages DB] → subscription → browser cache → DOM
Channel:  [Messages DB] → observer     → worker        → lens → provider API
```

Both directions of a channel:

- **Inbound** = external message arrives → figure out which user sent it → call `agent.send()` with that user's identity. Same as the web client's send button, except identity comes from a verified webhook instead of a browser session.
- **Outbound** = watch the messages database for new assistant rows, render them through the surface's lens, post them to every surface bound to that session.
- **The lens** = the one per-surface object: it renders outbound items into the surface's native form, and interprets inbound events back into a small fixed set of meanings (§8).

A channel introduces no concept the framework doesn't already have. The transcript is the existing messages collection. Identity is a userId. The turn is the existing loop. The live view is the existing `observeChangesAsync`.

### 4.2 What a channel is NOT

A channel does not add a new hook. The two existing hooks (`beforeProviderRequest` and `afterToolResult`) are the only points where app code can change what the agent does. Neither fires when a turn finishes. Outbound delivery is an *observer of committed database rows*, not a callback the loop triggers. This works because the loop already saves everything to Mongo — so a channel just reads Mongo. There's nothing to add to the loop itself.

## 5. The two framework changes

Only two things need to change in the core package. Each copies an existing pattern exactly.

### 5.1 `send`, `approve`, and `deny` get a server-side form

Today these functions only work through DDP (the browser's real-time connection). But the internal plumbing already accepts a plain `userId` parameter — the DDP method is just a thin wrapper that passes `this.userId` into the same internal function.

The change: expose `send`, `approve`, and `deny` directly on the `Agent` class so server-side code (like a webhook) can call them with an explicit user ID. This is the same refactor already done for `ask`, `fork`, and `compact`.

```js
// Server-side — mirrors the existing Agent.ask/fork/compact pattern
await agent.send(sessionId, 'What is my order status?', { userId: appUserId });
await agent.approve(sessionId, { userId: appUserId });
await agent.deny(sessionId, 'Not authorized', { userId: appUserId });
```

Two important rules:

- **Authorization is always fully scoped.** Every call checks that the session belongs to the given agent AND the given user. There's no "unscoped" mode that could accidentally match someone else's session.
- **`userId: null` is a real owner.** It means "anonymous / capability-URL owner," not "access denied." An unlinked external user gets an anonymous session — usable, just not tied to an account (§12).

**Rate limiting caveat:** The existing DDP rate limiter only sees browser calls. A webhook calling `send` directly bypasses it. The per-session budget (maximum turns) still applies to every caller. But a channel must add its own per-sender throttle at the webhook level, and should always use a capped agent.

### 5.2 An optional `channel` field on the session

Sessions already have optional fields like `parent`, `activeChild`, and `forkedFrom` that are absent by default and need no migration. The new `channel` field follows the same pattern:

```js
// On the session — optional, additive, migration-free
channel: { origin: 'sms', assurance: 'link' }
```

`origin` records which surface the session started on. `assurance` records how strongly the user's identity was proven (§12) — so a gate can require a stronger link before allowing a sensitive action.

This is a descriptor, not routing state (the bindings table handles that) and it holds no secrets, so it can safely be sent to the client. No new session phases or counters — delivery cursors live on the bindings.

## 6. The three tables

### 6.1 Identities — who is this person

```js
// ChannelIdentities
{
  _id: 'sms:+15551234567',       // kind + external user id
  kind: 'sms',
  externalUserId: '+15551234567',
  userId: 'meteor-user-id',      // the app account this is linked to
  assurance: 'link',             // how it was proven — see §12
  linkedAt: Date,
}
```

One app user can have many identity rows — Slack, SMS, and email all pointing at the same account. This table is what makes an agent recognize you across surfaces. If no row exists, the sender is unlinked and gets an anonymous session.

### 6.2 Bindings — which conversation maps to which session

```js
// ChannelBindings
{
  _id: 'sms:+15551234567',                   // kind + conversation key — derived, NOT random
  kind: 'sms',
  conversationRef: '+15551234567',
  destination: { to: '+15551234567', from: '+15559990000' },  // where replies go
  audience: 'direct',            // 'direct' (one recipient) or 'group' — set at bind time; §8.5 depends on it
  agent: 'support',
  sessionId: 'abc123',
  userId: 'meteor-user-id',
  externalUserId: '+15551234567', // who OPENED it — the key the claim-history pass matches on (§12)
  assurance: 'link',             // the opener's proof strength at bind time; 'none' when unlinked
  deliveredSeq: 5,               // "this surface has received everything up to message #5"
  claim: { serverId: 'srv-1', until: Date },
  createdAt: Date,
  updatedAt: Date,
}
```

**One session can have many bindings.** That's the point of the split. A session reachable from Slack and SMS has two binding rows, each with its own `deliveredSeq` and its own claim. When the agent answers, both surfaces get it, independently, at their own pace — if the SMS gateway is down, Slack still gets the reply and SMS catches up later.

The `_id` is derived (not random) so that two servers racing to bind the same conversation collide on the primary key — one wins, the other harmlessly fails.

**Important ordering:** when a new conversation arrives, insert the binding FIRST, then create the session. If you create the session first and lose the binding race, you've orphaned a session. Binding first means the loser created nothing and just adopts the winner's binding.

### 6.3 Receipts — what has actually been sent, and what reply it expects

```js
// DeliveryReceipts
{
  _id: 'deliver:sms:+15551234567:msg789',    // binding + message — NOT message alone
  state: 'sent',                             // 'sending' | 'sent' | 'abandoned'
  providerMessageId: 'SM8f2...',             // the surface's own id for what we posted
  expects: [                                 // present only when the delivery offered choices (§8.4)
    { match: 'YES', verdict: 'approved', toolCallId: 'tc_1' },
    { match: 'NO',  verdict: 'denied',   toolCallId: 'tc_1' },
  ],                                         // toolCallId names the exact ask a reply answers — §8.3
  attempts: 1,
  at: Date,
}
```

The `_id` includes the **binding**, not just the message: with fan-out, the same agent reply going to Slack and SMS is two different deliveries and needs two different receipts.

Receipts do three jobs. They make delivery effectively-once (§11). They record what an interactive delivery *expects back* — the reply grammar the lens registered when it rendered a prompt (§8.4). And `providerMessageId` is a durable correspondence between our messages and the surface's — the thing that makes threading, reactions, or edits mappable later, and whose absence is a documented failure mode in production chat bridges (§13).

### 6.4 The outbound worker

One worker per channel type, started at boot, stoppable, with two halves:

- **Observer:** watches the messages collection for new assistant rows. Provides low-latency notification.
- **Sweep:** runs every 15 seconds, catches expired claims and anything the observer missed.

Both halves are needed. The observer catches new messages instantly. The sweep catches claims that simply expired (server crashed mid-delivery) with no accompanying database write to trigger the observer.

The worker starts at boot (after indexes are ready), is gated by a settings flag so you can disable it per deployment, and is skipped during tests. **The worker never calls a model.** Delivery is a mechanical read-render-post path; it spends no tokens and cannot fail on a provider outage that has nothing to do with the surface.

### 6.5 One worker, not one-per-conversation

The worker runs ONE observer over all messages, not one observer per active conversation.

Why: a browser tab's subscription dies when the tab closes. An SMS conversation never closes. If you opened an observer per conversation, you'd accumulate observers forever as more conversations start, and nothing ever cleans them up. One shared observer with one periodic sweep keeps resource usage bounded, exactly how the existing watcher works.

### 6.6 Multi-server safety without Redis or leader election

Every race condition resolves through atomic conditional writes, never locks:

- Two servers try to deliver the same binding → one wins the claim, the other backs off.
- Two servers try to advance the same delivery cursor → one wins on the sequence guard.
- Two servers try to bind the same conversation → one wins on the derived `_id`, the other catches the duplicate-key error.

No Redis, no leader election, no lock table.

## 7. What gets sent — and who picks the destination

There are two kinds of outbound message. Mixing them up causes double-delivery.

**The reply is sent automatically by the worker.** When the agent finishes a turn and its last message has no tool calls (meaning it's the actual answer, not intermediate thinking), the worker renders it through each bound surface's lens and posts it. The agent doesn't "call a tool to reply" — replying is what the worker does.

**Deliberate side-actions are tools the agent chooses to call** — reacting, escalating to a human, sending an out-of-band notice.

### The destination is never a tool argument

A tool that takes a destination as an argument — `post(ref, text)` — lets whoever controls the model's output control where the message goes. That includes an attacker who plants instructions in a support ticket the agent reads. So: **the model chooses the text, never the destination.** The destination is looked up from the session's own bindings by trusted code:

```js
// The tool takes NO destination argument.
// It posts to the surfaces this session is already bound to — nowhere else.
// An inline tool spec, listed in the agent's `tools` array like any other.
tools: [{
  name: 'channel.notify',
  description: 'Send an out-of-band notice to this conversation.',
  args: { type: 'object', required: ['text'], properties: { text: { type: 'string' } } },
  gate: 'auto',
  async run(args, ctx) {
    const bindings = await ChannelBindings.find({ sessionId: ctx.sessionId }).fetchAsync();
    for (const b of bindings) {
      // Through the same three-phase receipt as the worker (§11), keyed on this
      // tool call's id. This is not optional: tool dispatch RE-RUNS on crash
      // recovery — the package's own comment calls that window "irreducible
      // without idempotency keys carried through to the tools themselves" —
      // so an unreceipted post here double-fires.
      await deliverOnce(b, { item: 'reply', text: args.text }, `tool:${ctx.toolCallId}`);
    }
  },
}],
```

If a tool genuinely needs to pick between surfaces, the argument is an enum of *this session's own bindings* — every option already authorized. It is never a free-form reference.

**The double-delivery trap:** don't give an agent a general "reply" tool. The worker already sends the reply. A reply tool would send the same text a second time.

### 7a. Approvals over a channel

If a tool has a `gate: 'ask'`, the agent pauses and the turn is parked as a document state — no process held open. The parked request becomes a `prompt` item (§8.2) that the worker delivers like anything else; the surface's answer comes back through the webhook as an approve/deny. The existing single-winner verdict system guarantees that if two people race to approve, only one vote counts.

Because the session records how strongly the user was identified, a gate can require a strong link for sensitive actions:

```js
gate: async ({ sessionId }) => {
  const session = await AgentSessions.findOneAsync(sessionId);
  return session?.channel?.assurance === 'oidc' ? true : 'ask';
}
```

## 8. The lens — one answer, many surfaces

Surfaces differ in exactly three ways that matter: how text is encoded (Slack's markup, email's HTML, SMS's plain 160 characters), how much fits, and how the user can act (buttons, reply keywords, links). Everything else about delivery is identical everywhere. The design splits along precisely that line: a **shared planner** decides *what* to deliver, and a small per-surface adapter — the **lens** — decides what it looks like there and what replies from there mean.

### 8.1 The canonical form already exists

The harness already commits everything a surface needs, as structure, not prose:

- The reply is `content` — an opaque string.
- Statuses are note rows carrying token fields. The package's own comment on the `reason` field says it exactly: *"a structured token, not a sentence — a UI renders its own prose from it."*
- The parked approval is `session.pending` with the tool's name, arguments, and identity.

And the web client already contains the pattern we need: one small function (`noteText`) that turns note structure into English sentences at the surface. A channel lens is another `noteText` — same structure in, different prose out.

What we do **not** do is invent an intermediate "universal message document" between the row and the surface. Prior art is brutal on this point: Microsoft's Adaptive Cards — a universal card language backed by one vendor — still renders differently across that vendor's own hosts, with hosts lagging the schema by years (§13). Ship semantic structure; let each surface encode it natively.

### 8.2 The planner's items — a closed set

The shared planner walks the committed rows past the binding's cursor and produces **delivery items**:

```js
{ item: 'reply',    text }                        // the turn's answer — opaque text, passed through
{ item: 'status',   kind, reason }                // error / budget / interrupted — turning tokens into prose is the lens's job
{ item: 'prompt',   name, args, runAs, toolCallId, choices }  // the parked approval; toolCallId names the exact ask; choices carry canonical tokens ('approve' | 'deny')
{ item: 'overflow', head, url }                   // what wouldn't fit: a mechanical head-slice plus a link to the web view
```

This set is **closed**, like the phase union, and asserted by a unit test. A channel cannot invent items — a lens must handle all four, and new items are a framework change, made deliberately. Prior art says keep this vocabulary brutally small: Rasa shipped a dedicated quick-replies type and later deprecated it because over-specified interaction types collapse back into the generic ones (§13).

Which `status` kinds a channel delivers is per-channel opt-in (an error is worth an SMS; a compaction note is not). Status kinds are the harness's *note* kinds — and one subtlety matters: the `approval` note is the **post-verdict audit record** ("approved by so-and-so"), which a channel may deliver as a status. The *ask itself* is never a status. It is always the `prompt` item, built from the parked state.

### 8.3 The lens: two halves of one object

```js
lens: {
  // Render an item into this surface's native form for a destination.
  out(item, destination) → payload | [payload],

  // Interpret a verified inbound event into one of a fixed set of meanings.
  in(event) → {
    intent,           // { kind: 'message', text } | { kind: 'verdict', verdict, reason?, toolCallId? }
                      //   | { kind: 'link-request' } | { kind: 'noop' }
    eventId,          // the provider's redelivery-stable id — powers dedup (§11)
    externalUserId,   // → identities table
    conversationRef,  // → bindings table
    destination,      // where replies to this conversation go
    audience?,        // 'direct' | 'group' — §8.5's capability-URL rule reads it; defaults to 'group' (the safe direction)
    respond?,         // noop only: a body the provider expects echoed in the 200 (Slack's URL-verification challenge)
  }
}
```

The intent set is closed too. `noop` covers the events every provider sends that mean nothing to the agent — URL-verification handshakes, delivery callbacks, bounces, message edits, reactions, read receipts, typing indicators, the bot's own echoes. In v1, anything without a defined meaning maps to `noop` *by design*, not by accident. `in` is also where surface grime dies: an email lens strips the quoted history below the new text before returning a `message`; a Slack lens ignores retry headers. And `link-request` is optional — a lens with no gesture for it (a keyword, a slash command, a home-tab button) simply never emits it, and linking can always start from the web side instead (§12).

**Why the two halves live in one object.** On a surface with no buttons, the approval prompt renders as *"Reply YES to approve, NO to deny."* The words YES and NO are now a parse grammar — inbound text only means "approved" because the outbound render said it would. The two halves are one artifact; splitting them across a render function here and a webhook parser there is how they drift. Microsoft's Bot Framework unified outbound rendering but left inbound button semantics per-channel — the same button click sends back its value on one surface and its title on another, and bots ended up branching per channel anyway (§13). The lens closes that hole by construction.

**Interpreting a reply requires remembering what was offered.** "YES" from a phone number is a verdict *only if* an approval prompt is outstanding on that binding — otherwise it's just a message. So when `out` renders a prompt, the delivery receipt records the expected replies (`expects`, §6.3), and the inbound side checks the binding's outstanding receipt before falling through to "this is a message."

Two staleness rules make this safe. Each `expects` entry names the exact ask it answers (its `toolCallId`), and the router drops a matched token whose ask is no longer the one currently parked — so a YES aimed at last week's request cannot approve today's different one. And beneath that, the existing single-winner verdict write remains the final authority: a stale YES that slips through maps to an approve call that harmlessly loses the race.

This shape has a name in the functional-programming literature: a **lens**, a paired *get* (render out) and *put* (interpret in), where put gets access to the original context precisely because the rendering was lossy. We keep the shape, the receipt-carrying put, and one law; we deliberately drop the algebra (composition frameworks, the law zoo) — adapters here compose through the message hub, not through each other.

**The one law, as a test.** For every item the planner can emit under a channel's profile: render it, then feed each offered affordance's synthetic inbound event back through `in`, and require the exact canonical intent. If a lens renders a button, it must interpret the click; if it renders "Reply YES," it must interpret YES. One property test per channel, runnable without any provider — shipped as `assertLensRoundTrip` (§8.7).

### 8.4 Interaction: three grammars, one meaning

The profile declares how choices are offered on this surface:

```js
profile: { interact: 'native' | 'menu' | 'link', limit?: number }
```

- **`native`** — the surface has real affordances (buttons, quick replies, rich-card suggested actions). The lens renders them and wires each postback to carry the canonical token, so interpretation doesn't depend on provider quirks. `interact` governs how choices are *offered*, not what inbound is accepted — a Slack user who types YES instead of clicking still lands in `in` as a message.
- **`menu`** — no affordances, but replies are cheap (SMS). The prompt renders as a reply menu — *"Reply YES to approve, NO to deny"* — and registers those tokens in the receipt's `expects`. This is the pattern the entire SMS/IVR industry converged on: on a widgetless surface, the interaction contract is a parse grammar over inbound text.
- **`link`** — replies are awkward or unparseable (email, one-way notification surfaces). Each choice renders as a **one-time URL** carrying a single-use random token stored server-side (unguessable, expiring, bound to its subject — here the specific pending verdict; no key management). This is the same token *primitive* account linking uses (§12), with a different subject: a linking token is bound to an external identity, an approval token to one pending verdict. They are never interchangeable.

All three land inbound in the same place: a `verdict` intent. The grammar registered is exactly the affordance offered, which is exactly what the round-trip test checks.

### 8.5 Degradation rules

Each of these is a lesson somebody else already paid for (§13):

- **Plain text is the floor.** Every item must have a plain-text rendering, and `content` already is one. Matrix makes a plain-text body mandatory on every formatted message for exactly this reason: every adapter can always emit *something*.
- **Fallbacks are separate values chosen whole, never markup embedded in content.** Matrix's in-band reply fallback — HTML receivers had to find and strip — caused client security vulnerabilities and is being removed from their spec. Our items are sidecar structure; a lens selects, it never parses-and-strips.
- **Every rendering is derived mechanically from the committed row at delivery time.** Never authored in parallel: email's multipart/alternative proves hand-maintained alternatives drift stale.
- **Degrade per item, not per message.** One unrenderable element must not flatten the whole delivery to its poorest form — the message's text still goes out rich even if a prompt degrades to a link.
- **When it truly doesn't fit, the web is the escape hatch.** Over the profile's `limit`, the planner emits `overflow`: a mechanical head-slice of the text plus a link to the session's web view. No summarization — the worker never calls a model. Email practitioners reached the same conclusion about rich-content degradation: treat the fallback as the primary experience. One restriction: for an anonymous session the web URL *is* the credential (§12), so it may only be sent to a `direct` destination — a DM, a phone number, an email address. Into a `group` surface (§6.2) the planner sends the head-slice without the link; owned sessions may link everywhere, because their URL is login-gated.
- **Markdown stays opaque in the core.** The model may emit markdown; the harness treats `content` as an unparsed string (the web client renders it literally, through `textContent`, on purpose). A lens that wants to convert it — to Slack's markup, to HTML for email — opts in inside its own `out`. No markdown parser enters the shared core; parsing model output is a per-surface choice with per-surface risk.

### 8.6 What the lens refuses to be

- **Not a universal layout language.** The planner ships semantic structure; the lens encodes natively. (§13's central negative result.)
- **Not a lowest common denominator.** SMS's 160 characters must not decide what Slack receives; degradation is per-surface, downward from the full row.
- **Not an escape hatch that becomes the API.** `out` returning provider-native payloads *is* the passthrough tier, so there is no separate raw channel to grow around the vocabulary. The smell to watch: if lens authors routinely need to bypass the planner's items, the closed set is too poor — extend it deliberately, in the framework, once.
- **Not stateless where references are involved.** Edits, reactions, and threading all reference prior messages; production chat bridges that translate them statelessly misattach them. Out of scope for v1 — but the receipt's `providerMessageId` is the correspondence table that makes them possible without a redesign.

### 8.7 Who uses the lens, and how

The lens has four users, on a ladder — and the design succeeds when the first two never know it exists.

**The human on the surface never sees it.** Their entire experience of the lens is that answers arrive looking native — blocks in Slack, 160 clean characters in SMS — and that replying naturally *works*: they text back YES and the refund goes through. The lens is why YES means something. That invisibility is the success criterion.

**Most app developers install one and write no rendering code.** A channel package is one lens, one transport, one profile default — so the common path is configuration only:

```js
import { slack } from 'meteor/10thfloor:agent-channel-slack';

Agent.channel('slack', slack({
  agent: 'support',
  botToken: Meteor.settings.packages['10thfloor:agent'].slack.botToken,
  signingSecret: process.env.SLACK_SIGNING_SECRET,
}));
```

Note that nobody ever *calls* a lens. The worker calls `out` at the delivery edge; the webhook calls `in` at the ingress edge. Developers only supply it.

**A developer with opinions overrides one item.** The closed vocabulary is what makes customization surgical: "change how errors read" or "use our branded blocks for replies" is one function, and the API for it is deliberately just object spread — over the definition the factory returns (the factories take no `lens` option) and over the package's stock lens — no combinator framework:

```js
import { slack, slackLens } from 'meteor/10thfloor:agent-channel-slack';

const def = slack({ agent: 'support', /* …secrets */ });
Agent.channel('slack', {
  ...def,                               // the factory returns the plain definition (§10)
  lens: {
    ...slackLens,
    out: (item, dest) =>
      item.item === 'reply'
        ? myBrandedBlocks(item.text)      // yours
        : slackLens.out(item, dest),      // everything else: stock
  },
});
```

Overriding `reply`, `status`, or `overflow` is prose-only and can't break the contract. Overriding `prompt` is the one that can — you might render choices `in` no longer understands — and that is exactly what the round-trip test catches, so a customization that drifts fails in CI, not in a customer's thread.

**A surface author writes one: two halves, a profile, one test.** A new surface is a few dozen lines:

```js
export const discordLens = {
  out(item, dest) {
    switch (item.item) {
      case 'reply':    return { content: item.text };
      case 'status':   return { content: statusProse(item) };   // your second noteText
      case 'prompt':   return { content: askText(item), components: buttons(item.choices) };
      case 'overflow': return { content: item.url ? `${item.head}\n${item.url}` : item.head };
    }
  },
  in(event) {
    if (event.type === 'MESSAGE_COMPONENT') return { intent: { kind: 'verdict', verdict: event.data.custom_id }, ...envelope(event) };
    if (event.type === 'MESSAGE_CREATE' && !event.author.bot) return { intent: { kind: 'message', text: event.content }, ...envelope(event) };
    return { intent: { kind: 'noop' }, ...envelope(event) };
  },
};

// the one law (§8.3), as the framework ships it:
assertLensRoundTrip(discordLens, { interact: 'native', limit: 2000 }, {
  // Only the lens author knows a click's wire shape — build it from the
  // ACTUAL rendered buttons, so drift between out() and in() fails here.
  synthesize: (choice, rendered) => ({
    type: 'MESSAGE_COMPONENT', data: { custom_id: buttonFor(rendered, choice).custom_id },
  }),
  message: (text) => ({ type: 'MESSAGE_CREATE', content: text, author: { bot: false } }),
});
```

`assertLensRoundTrip` is a shipped helper doing two jobs: **totality** — all four items produce a payload, so no surface silently drops an approval ask — and **round-trip** — every affordance `out` offers, `in` interprets back to the exact canonical intent. Both halves are pure, so the test runs with zero provider credentials.

The ladder, then: use it without knowing → install it → override one item → author one. Each rung is opt-in, and each is safe for the same two reasons: the vocabulary is closed, and the contract is a test.

## 9. Inbound — the webhook

With the lens in place, the webhook pipeline is the same for every channel; nothing in it is provider-specific:

```
verify signature → lens.in(event) → throttle → claim eventId → route by intent
```

1. **Verify** the provider's signature (401 if invalid — this is the trust boundary).
2. **Interpret**: `lens.in` turns the raw event into an intent plus the routing envelope. Interpretation is pure — no side effects yet.
3. **Throttle** per sender — throttled events are dropped with a 200, not refused with a 429: providers retry non-2xx and count failures toward disabling the integration, so a 429 would let one abusive sender degrade the whole channel (ingress.ts). The throttle comes before the claim because the throttle is a counter and the claim is a database write — a flood of validly-signed events must not buy an insert each. A throttled event is settled and forgotten; it buys neither a write nor a provider retry.
4. **Claim the event id** (§11). A provider retry collides here and gets a 200 without running anything twice.
5. **Route by intent:**
   - **Admission and identity:** the calls below run as the SENDER's own resolved identity (or `null`, anonymous) — never the binding's owner as a fallback, which would let any unlinked participant in a group thread act as the linked owner. On a `group` surface an anonymous conversation admits only its opener until someone links (§3); a non-opener is settled silently with a 200.
   - `message` → resolve identity, find-or-create the binding (binding first, then session), then `agent.send()` — never a direct database insert; sequence numbers are allocated atomically inside `send`, and a direct insert would race the running loop.
   - `verdict` → `agent.approve()` / `agent.deny()`. The channel carries identity to the agent's approve predicate; the predicate decides.
   - `link-request` → the account-linking flow (§12).
   - `noop` → 200, done.

Free text while a prompt is outstanding is the one ambiguous case, and §8.3's receipt check resolves it: match against `expects` first, fall through to `message`.

## 10. Configuration

Everything channel-specific now lives in two places: the lens (behavior) and the profile plus secrets (facts). The webhook's trust boundary is two functions on the definition — `verify` (does this request really come from the provider? a false is a 401 — §9 step 1) and `parse` (raw request → the provider event `lens.in` reads) — and the package factory supplies both, wrapping the secret, so the install-only path (§8.7) never writes them:

```js
import { sms } from 'meteor/10thfloor:agent-channel-sms';
import { slack } from 'meteor/10thfloor:agent-channel-slack';
const cfg = Meteor.settings.packages['10thfloor:agent'];

Agent.channel('sms', sms({
  agent: 'support',
  accountSid: cfg.sms.accountSid,             // AC…
  authToken: cfg.sms.authToken,               // also the signature key `verify` uses
  webhookUrl: cfg.sms.webhookUrl,             // the EXACT public URL Twilio calls — its signature covers it
}));

Agent.channel('slack', slack({
  agent: 'support',
  botToken: cfg.slack.botToken,
  signingSecret: cfg.slack.signingSecret,
  statuses: ['error', 'budget', 'approval'],  // note kinds to deliver; 'approval' = the post-verdict outcome, never the ask (§8.2)
}));
```

A factory is sugar over the plain definition — what a surface of your own writes:

```js
Agent.channel('sms', {
  agent: 'support',
  transport: smsTransport({ accountSid, authToken }),
  lens: smsLens,                              // { out, in } — §8.3
  profile: { interact: 'menu', limit: 1500 },
  verify: (raw) => verifyTwilioSignature(raw, authToken, webhookUrl),
  parse: (raw) => parseTwilioForm(raw.rawBody),
  statuses: ['error', 'approval'],            // which status kinds this surface delivers
  onUncertainDelivery: 'retry',               // 'reconcile' | 'retry' | 'abandon' — §11; optional, defaulted from the transport
});
```

- **Secrets** come from settings or environment variables, never inline.
- **`onUncertainDelivery` is optional.** Unset, it defaults to `'reconcile'` when the transport supplies `reconcile`, else `'retry'` — §11 says when that default is wrong and a channel must declare.
- **Bindings and identities are created at runtime**, never hand-authored.
- Channels are **on by default** and can be disabled per-kind for deployments that run delivery on one designated instance.
- A channel package (`agent-channel-sms`, `agent-channel-slack`) is exactly one lens, one transport, and one profile default — nothing else, because everything else is shared. §8.7 shows the resulting developer experience, from install-only to authoring a new surface.

## 11. Delivery guarantees — being precise

**Exactly-once on the way in; effectively-once on the way out.** The two directions are different problems.

### Inbound: exactly-once admission — genuinely achievable

Providers retry. Slack resends an event if you don't answer in 3 seconds; Twilio retries on any non-2xx. Without dedup, one user message produces two agent turns — double the spend and often two contradictory answers.

Every provider supplies a redelivery-stable event ID, and the lens's envelope surfaces it uniformly. Before doing any work, claim it:

```js
// Derived _id — a retry collides on the primary key and is rejected outright.
try {
  await InboundSubmissions.insertAsync({ _id: `${kind}:${eventId}`, at: new Date() });
} catch (e) {
  if (isDuplicateKey(e)) return res.end();   // already admitted; no second turn
  throw e;
}
```

This holds across servers because it's one atomic insert. As built the idiom is one helper, `insertOrLose` (`server/channels/collections.ts`): insert on a derived `_id`, `true` if this caller won, `false` on duplicate key, anything else propagates — shared by the binding insert, session repair, this admission claim, the receipt reserve and the identity row.

### Outbound: effectively-once — and why it can't be more

Posting to a provider and recording that you posted are two writes to two systems with no shared transaction. If the process dies between them, nothing can tell you which side happened. This is the Two Generals problem; any framework claiming true exactly-once delivery to a third-party API is redefining the term.

What is achievable: **the surface displays the message exactly once.** The worker uses a three-phase intent log:

1. **Reserve** — insert a receipt in state `sending`. Duplicate key means someone else has it or it's done.
2. **Post** — call the provider, passing a provider-side idempotency key where supported.
3. **Confirm** — mark the receipt `sent`, then advance the binding's cursor.

A crash between 2 and 3 leaves a `sending` receipt — the one genuinely ambiguous state. Recovery depends on what the provider offers, and the channel must declare its tier:

| Tier | Provider capability | Recovery | Result |
|---|---|---|---|
| **A** | Honors an idempotency key (Twilio-style) | Retry with the same key; the provider collapses it | Effectively-once |
| **B** | Lets you read back what you posted | Read the destination, look for the receipt id, post only if absent | Effectively-once |
| **C** | Neither (raw SMTP, some gateways) | No way to know | **Declared choice: `retry` (may duplicate) or `abandon` (may lose)** |

Leaving tier C undeclared just means picking one by accident. As built, the field is optional and defaults to `'reconcile'` when the transport supplies `reconcile` (tier B), else `'retry'` (the tier-A assumption — safe when the provider honours the idempotency key, MAY DUPLICATE on tier C). A tier-C transport cannot be told apart from tier A by shape, so tier-C channels SHOULD declare `'retry'` or `'abandon'` explicitly (`uncertainDeliveryMode`, registry.ts).

The receipt table also fixes a subtler bug: the observer replays the whole backlog when a server boots. Without receipts, every deploy re-sends old messages. With them, the backlog pass finds everything already `sent` and does nothing.

## 12. Account linking

This is the one genuinely new trust decision channels introduce. An external user ID tells you who *claims* to be speaking. It is identification, not authentication. Turning it into an app account requires proof.

### How to do it

**Preferred — an OAuth/OIDC round-trip** where the surface supports one (Slack does, via Sign in with Slack). The user, already authenticated in your web app, proves control of the external account; both sides are proven in one flow. Record `assurance: 'oidc'`.

**Fallback — one-time link** for surfaces without OAuth (SMS, email). The agent sends a link carrying a single-use random token stored server-side (unguessable, expiring, bound to its subject — the specific external identity it will link; no key management). The user opens it while authenticated in the web app; the server burns the token and writes the identity row. Record `assurance: 'link'`.

**Direction matters.** Linking must be completed from the authenticated side. An unauthenticated inbound message can *request* a link; it can never *assert* one.

### What not to do

- **Never auto-link on matching email addresses.** An external profile email is not proof of mailbox control — in many workspace configurations it's admin-set and unverified. Auto-linking on email match is an account-takeover primitive.
- **Never treat a phone number as identity for anything privileged.** SIM swap is routine. Fine for "what's my order status," not for "refund my order."
- **Never trust an external user ID by itself.**

### Assurance levels do real work

| Assurance | Meaning | Gets |
|---|---|---|
| `none` | Unlinked | Anonymous session; no account data; capability-scoped |
| `link` | Proved via one-time link | Normal capability |
| `oidc` | Proved via OAuth round-trip | Full capability, including sensitive tools |

Gates read this directly (§7a), so "require a real login before issuing a refund" is a one-line predicate rather than a parallel permission system.

### Claiming history at link time

A user who talks to the agent before linking has anonymous sessions. When they link, those sessions should become theirs — a guarded rewrite of the owner on the bindings and sessions created by that external identity. Worth specifying explicitly, because the alternative is silently losing a user's history the moment they sign in.

## 13. Prior art

### Flue

[Flue](https://flueframework.com/) (the Astro team's agent framework) has the closest channel concept. We independently agreed on derived conversation IDs and the verified webhook as the trust boundary. We took two things: **destination binding** (their tools guide is explicit that tool arguments are not authorization boundaries — our earlier draft passed the destination as a model-supplied argument, a real prompt-injection hole, now fixed in §7) and **inbound idempotency keys** (§11). We differ deliberately: our replies are implicit (worker-delivered) where theirs are model-invoked tools; our authorization lives in the framework rather than HTTP middleware; and we specify account linking (§12), which their docs leave to the application.

### The rendering lineage

The lens design (§8) is built on lessons from thirty years of "one message, many surfaces":

| System | What it teaches | Where it landed here |
|---|---|---|
| Email `multipart/alternative` | Sender-enumerated alternatives work — but hand-authored ones drift stale | Renderings derived mechanically at delivery time (§8.5) |
| Microsoft Bot Framework | A typed canonical message works; the abstraction leaks *inbound* (the same button click returns different fields per channel) | The lens pairs render and interpret in one object (§8.3) |
| Adaptive Cards | Even one vendor can't make a universal layout language render consistently across its own hosts | No intermediate document format; semantic items, native encoding (§8.1) |
| Matrix `body` + `formatted_body` | A mandatory plain-text projection is the cheapest, most battle-tested floor | Plain text is the floor (§8.5) |
| Matrix reply-fallback removal | In-band fallbacks receivers must parse-and-strip become security vulnerabilities and get ripped out of specs | Fallbacks are sidecar values selected whole (§8.5) |
| Production chat bridges (Matrix↔Slack/WhatsApp) | The hard 20% is reference-carrying features; stateless translation misattaches them | `providerMessageId` on the receipt is the correspondence table (§6.3) |
| Rasa / Botpress | Keep the semantic vocabulary brutally small; over-specified types get deprecated | Four items, closed set (§8.2) |
| SMS/IVR practice | On a widgetless surface, interaction *is* a parse grammar generated by the outbound prompt | The `menu` grammar and receipt `expects` (§8.4) |
| Lens literature (Foster et al.) | get/put with round-trip laws; put needs the original context because get is lossy | The shape, the receipt-carrying `in`, and exactly one law as a property test — the algebra dropped (§8.3) |

## 14. Things deliberately NOT added

- **No new hook** on the loop. Outbound delivery observes committed rows.
- **No channel class hierarchy.** A channel is one lens, one transport, one profile.
- **No universal message/card format** between the row and the surface (§8.1).
- **No markdown parser in the shared core.** Content stays opaque; conversion is a per-lens opt-in (§8.5).
- **No hand-authored parallel renderings.** Everything is derived from the committed row at delivery time.
- **No per-conversation observers.** One worker with a sweep.
- **No token streaming to non-web surfaces.** Turn-at-a-time.
- **No hand-authored bindings or identities.** Both are runtime state.
- **No new session phases or counters.** Delivery cursors live on bindings; approval parking uses the existing machinery.
- **No Redis or leader election.** Atomic conditional writes everywhere.
- **No claim of true exactly-once delivery.** §11 says exactly where the line is instead.
- **No model calls in the delivery path.** Rendering is mechanical; overflow is a head-slice, not a summary.

## 15. Open questions

- **Package vs. app code.** Resolved: `Agent.channel` ships in the package; provider SDKs live in the channel packages.
- **Attachments and media.** Inbound images (MMS, Slack uploads) have no place in the current item vocabulary or in `AgentMessage`. Probably a framework-level question before a channel-level one.
- **Read-back reconciliation coverage.** Tier B recovery (§11) needs per-provider verification of what can actually be read back, and from where, before a transport claims that tier.
- **Group conversations.** A binding carries one owner and every agent call is owner-scoped, so v1 is single-human by construction (§3). A shared session with per-message attribution is a real ownership-model question for the framework, not a channel detail.
- **Provider send policies.** Some surfaces refuse messages outright by policy — WhatsApp's 24-hour customer-service window and pre-approved templates are the canonical case. The receipt's `abandoned` state absorbs the failure, but *choosing a compliant fallback rendering* (an approved template instead of free text) is unspecified.
- **Unlinking.** Removing an identity row stops future routing, but what happens to sessions it created — orphaned, reassigned, or deleted? Matters for data-deletion requests.
- **Localization.** The lens turns status tokens into prose (§8.1), which is where per-language rendering would slot in — one more argument for prose living at the surface, but unspecified.

## 16. Next steps

Build **SMS and Slack together as the proving pair** — not Slack first. SMS is the design's stress test: `menu` interaction, a hard length limit, tier-A idempotency, weak identity. Slack is the rich end: `native` interaction, threading, tier-B read-back, OIDC linking. The lens contract, the profile, and the degradation ladder are only proven by the pair; either one alone lets surface-specific assumptions hide in the shared core.
