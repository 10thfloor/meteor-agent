# Constellation execution and evidence rollout

Accepted scope: extend meteor-agent and its local Electron application with the
patterns identified in the Mastra review. Meteor owns persistence, methods,
authorization, reactivity, scheduling, and runtime coordination.

## Delivery checklist

- [x] Evidence: durable traces/spans, resolved capability and memory manifests,
  safe display/model/transcript tool projections, audit feedback.
- [x] Missions: versioned declarative plans composed from registered primitives;
  coordination choices; durable runs, checkpoints, approval, stop, and guarded
  replay; delegation context and budget boundaries.
- [x] Memory: source-linked observations and reflection candidates through the
  existing experience/practice governance; inspect memory available at turn start.
- [x] Federation: authenticated, revocable local MCP exposure; consume remote
  resources and prompts through the configured server boundary.
- [x] Evaluation Lab: versioned scenarios, deterministic gates, isolated runs,
  stored experiments, comparison, and extension hooks for custom scorers.
- [x] Constellation: plan/run controls in Missions; activity and memory evidence
  on demand; a separate evaluation surface; federation beside MCP configuration.
- [x] Verification: static and package/app gates; real browser flow checks;
  local Electron launch; document public APIs and operational limits.

## Usability acceptance criteria

Apply Steve Krug's principles: visible choices, familiar controls, obvious
click targets, useful defaults, concise functional copy, and clear recovery.

- A new user can find Plan, Run, Stop, Review, and Retry without opening settings.
- Configuration is separate from run history; saved versions remain identifiable.
- Active work shows animated progress and a readable status; reduced motion works.
- Empty states provide the next useful action. Errors stay beside their controls.
- Every field has a label. Keyboard focus, dialog dismissal, and return focus work.
- Use text as well as color for state; keep ordinary chat free of raw JSON.
- Advanced details are disclosed on demand; no narrative section introductions.
- Evidence distinguishes recalled memory, observations, and validated learning.

## Existing boundaries to preserve

Leased session execution and exact approval receipts remain authoritative.
Live agent identity must not be changed by evaluations. Automatic learning obeys
the existing individual experience/practice admission policies. Replay must not
silently repeat an uncertain side effect. External access is opt-in and scoped.
The existing modification to `app/.meteor/versions` belongs to the user.

## Where to use it

- **Missions → Plan & runs:** configure agents, tasks, dependencies, review
  checkpoints, coordination strategy, and limits. Save a version, run it, and
  inspect individual results. Stop/retry/restart controls appear only when
  applicable; side-effecting steps cannot silently replay.
- **Runs → View evidence:** inspect the selected step's activity and frozen
  memory. The Conversation selector also exposes the main mission chat.
- **Crew → Learning → Reflect after replies:** opt in to model reflection.
  Experience and Practice admission remain separate existing policies.
- **Evaluation Lab:** create scenario sets, configure expected/avoided phrases
  and tool selection, optionally supply synthetic memory, then compare agents
  and saved runs. Editing a scenario creates a version; previous results retain
  their original scenario.
- **Capabilities → MCP servers → Share access:** create a revocable token,
  select agents/missions, and explicitly enable the local MCP endpoint.
  Resources & prompts inspects content from an existing configured MCP server.

## Deliberate limits

- Federation accepts loopback connections only. Cross-machine federation,
  organization federation, public hosting, and new authentication flows are
  not part of this local rollout.
- Evaluation tool calls are proposals, not executions. Synthetic memory is
  context, not an alternate live identity; evaluations never train the Crew.
  Custom/model scorers are developer-registered extension hooks, not a built-in
  claim of objectively measured agent quality.
- A memory manifest proves what was available at turn start, not which facts
  the model relied on. Explicit searches appear separately in Activity.
- Offline reflection preserves source observations and supports manual drafts;
  a live configured provider is needed for model-generated reflection.
- Trace storage does not collect hidden reasoning or raw provider prompts.

## Verification results

- Package suite: 877 server and 30 client tests passed; zero failures and one
  existing pending test.
- Full-app suite: 55 server and 52 client tests passed; zero failures.
- Type checking, declaration generation, downstream type-consumer checks,
  release validation, desktop checks, JavaScript syntax, and diff whitespace
  checks passed.
- Native Electron flow checks covered saving a plan, running its agent step,
  approving a checkpoint, viewing results and source-linked evidence, opening
  an experience draft without admitting it, and comparing two evaluations.
  Loading states, keyboard controls, and clean output were checked in the app.
- Interactive checks used the offline provider. Live model quality and remote
  provider integrations were not assessed. Local MCP authentication, scopes,
  and revocation were exercised in isolated tests; workspace sharing stays off.
